## Root Cause Assessment

The API pod OOM event is consistent with an application-side memory leak. In Store.cache_set, every cache write also stores the payload into an in-process dict (self.local_cache) that has no eviction and is never read for serving requests. Each GET /orders/<id> call grows this dict unbounded, which can push the process toward the 256Mi container limit and trigger OOM. This directly explains the RESOURCE_ERROR memory warnings followed by a Gunicorn worker SIGKILL.

## Reasoning

The RCA's symptom (memory at ~94% of 256Mi then worker SIGKILL) is plausibly caused by the unbounded local in-process cache. The code path: GET /orders/<id> -> store.cache_set() -> self.local_cache[...] = payload with no eviction or size bound. This leak accumulates per order access and is independent of Redis. Removing the unintended local cache write is the smallest change that addresses the underlying defect without altering external behavior. Kubernetes manifests need not change to resolve the root cause.

## Discrepancies

- RCA recommends increasing Kubernetes memory limits in k8s/api.yaml as the primary remediation, but the repository reveals an unbounded in-process cache in api/store.py causing memory growth.
- CHAOS endpoints are enabled by default in the provided ConfigMap (CHAOS_ENABLED: "true"), which is risky, but not necessary to reproduce the leak since cache_set writes to local_cache on every cached fetch.
- No evidence in the repo suggests that higher limits are the correct durable fix; raising limits would mask the leak rather than address it.

## Changes Applied

- `Orders_Platform/api/store.py`
  - Eliminate the unbounded in-process cache growth. local_cache is intended for chaos-induced memory leak experiments, not normal caching; writing every payload into it creates a persistent memory leak driving the pod toward its memory limit.
